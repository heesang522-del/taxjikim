# 로그인 실패 흐름 검토

현재 구현을 설명한 문서다. 최종 확정안이 아니며, 각 단계의 동작을 확인하면서 수정 방향을 정한다.

## 1. 아이디 입력

- 아이디 입력만으로 서버에 요청하지 않는다.
- 새로고침 후에도 로그인 버튼을 눌렀을 때만 차단 상태를 확인한다.

## 2. 로그인 버튼 클릭

서버가 다음 순서로 확인한다.

차단 중이면 로그인 요청의 응답으로 남은 시간을 전달한다. 화면은 이 응답을 받은 뒤 차단 안내를 표시한다.

1. 회원의 계정 상태 확인
2. 일시 차단 여부 확인
3. 비밀번호 확인

- 이미 잠기거나 이용 정지된 회원은 로그인할 수 없다.
- 일시 차단 중에는 비밀번호를 검사하지 않는다. 올바른 비밀번호여도 차단이 끝나야 시도할 수 있다.

## 3. 로그인 실패

- 비밀번호가 틀리면 아이디별 실패 횟수를 Redis에 기록한다.
- 존재하지 않는 아이디도 실패 기록을 쌓는다. 다만 변경할 회원이 없으므로 DB 잠금은 수행하지 않는다.
- DB 조회 장애는 로그인 실패 횟수에 포함하지 않는다.

| 누적 실패 | 처리 |
| --- | --- |
| 1~5회 | 실패 안내와 첫 잠금까지 남은 횟수 표시 |
| 6회 | 30초 차단 |
| 7회 | 1분 차단 |
| 8회 | 3분 차단 |
| 9회 | 5분 차단, 다음 실패 시 최종 잠금 안내 |
| 10회 | 실제 회원이면 DB 상태를 `LOCKED`로 변경 |

## 4. 일시 차단 중

- 서버는 추가 요청의 실패 횟수를 늘리지 않는다.
- 차단 종료 시각도 연장하지 않는다.
- 화면은 남은 시간을 표시하고 로그인 버튼을 비활성화한다.
- 카운트다운은 화면에서만 갱신하며 매초 서버 요청은 하지 않는다.

## 5. 일시 차단 종료

- 로그인 버튼을 다시 사용할 수 있다.
- 실패 횟수는 초기화되지 않는다.
- 한 번 더 실패하면 바로 다음 차단 단계로 넘어간다.

예: 6회 실패 → 30초 대기 → 다시 실패 → 7회 실패로 1분 차단.

## 6. 로그인 성공

- 정상 상태의 회원이고 일시 차단 중이 아닐 때 비밀번호를 확인한다.
- 비밀번호가 맞으면 실패 횟수와 차단 기록을 삭제한다.
- 이후 기존 HttpOnly JWT 쿠키 로그인 처리를 진행한다.
- 실패 기록에는 자동 만료를 설정하지 않았다. 시간 경과만으로 초기화되지 않는다.

## 7. 최종 잠금 및 해제

- 10회 실패한 실제 회원은 `LOCKED`로 저장한다.
- 잠금 상태에서는 올바른 비밀번호를 입력해도 로그인할 수 없다.
- 로그인 실패 응답으로 바깥 트랜잭션이 롤백되더라도 DB 잠금이 유지되도록 인증 트랜잭션을 분리했다.
- 현재 구현에서는 관리자가 해제한다. 해제 시 회원 상태를 `ACTIVE`로 바꾸고 실패 기록과 기존 로그인 세션을 삭제한다.
- 해제 후 새로 로그인할 수 있으며, 다음 실패는 1회부터 집계한다.
- `LOCKED`는 로그인 실패 잠금, `BANNED`는 관리자 이용 정지로 구분한다.
- 이메일을 통한 잠금 해제는 현재 구현에서 중단된 상태다. 이메일 인증 통합은 별도 티켓에서 검토한다.
