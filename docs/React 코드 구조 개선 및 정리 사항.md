# React 코드 구조 개선 및 정리 사항

## 작성 목적

기능을 수정할 때 관련 코드를 쉽게 찾고, 다른 기능에 미치는 영향을 줄이기 위해 React 코드의 역할과 정리 방향을 설명한다.

## 개선 항목

| 항목 | 개선 방향 |
| --- | --- |
| 코드 역할 분리 | 페이지·컴포넌트·모달·네비게이션이 맡은 역할에 집중하도록 구성 |
| 화면 영역 분리 | 입력·목록·요약 등 기능 영역을 컴포넌트로 나누고 배치 |
| 미사용 코드 정리 | 사용 여부와 API 대체 여부를 확인한 뒤 불필요한 코드 삭제 |

## 1. 역할에 따라 프론트 코드를 나눈다

### 개선 목적

네비게이션은 이동 메뉴에 집중하고, 페이지는 화면을 구성하며, 모달과 컴포넌트는 맡은 기능에 집중한다. 화면 영역과 폴더를 구분하라는 내용도 같은 방향이다. 한 파일을 수정할 때 관계없는 기능까지 함께 살펴보지 않도록 역할을 나누는 것이 목적이다.

### 문제

하나의 파일에 화면 배치, 긴 모달 내용, 서버 통신, 공유 상태 관리 등이 섞이면 수정할 위치와 영향 범위를 파악하기 어렵다.

### 수정 방향

#### 폴더와 페이지의 역할

| 위치 | 역할 | 예시 |
| --- | --- | --- |
| `front/src/pages/` | 주소에 해당하는 화면을 구성하고 기능의 흐름을 연결 | 게시글 상세 페이지에 본문·댓글·신고 모달 배치 |
| `front/src/components/` | 화면의 개별 영역이나 재사용 요소 구현 | 댓글 목록, 입력 폼, 신고 모달 |
| `front/src/api/` | 공통 client를 이용한 서버 요청·응답 처리 | 게시글 조회, 댓글 등록 |
| `front/src/store/` | 여러 컴포넌트·화면에서 공유하는 상태 관리 | 로그인 상태 |
| `front/src/utils/` | 공통 보조 처리 | 날짜·금액 표시 형식 변환 |
| `front/src/styles/` | 공통 스타일과 배치 규칙 | 색상, 간격, 그리드 |

페이지는 필요한 컴포넌트를 조합하고, 컴포넌트는 맡은 화면 영역에 집중한다. API 요청 구현은 `api/`에 두고, 페이지·컴포넌트 또는 관련 기능 로직에서 해당 함수를 호출한다. 페이지에 로직을 전혀 두지 말라는 의미는 아니다.

#### 모달의 역할

공통 `Modal`은 배경·창의 틀·닫기 동작을 담당한다. 기능별 모달은 입력과 표시를 담당하고, 제출 이벤트를 상위에 전달하거나 해당 기능 로직에 연결한다. 모달마다 전용 페이지를 만들거나 모든 모달 내용을 페이지 파일에 작성하라는 뜻은 아니다.

모달 열림이나 입력값처럼 한 곳에서만 필요한 상태는 해당 컴포넌트에서 관리한다. 모든 상태를 store로 옮기지 않는다. 작은 함수까지 무조건 별도 파일로 나누지 않고 역할과 복잡도를 기준으로 판단한다.

#### 네비게이션과 라우터의 역할

| 구분 | 쉬운 설명 | 프로젝트 예시 |
| --- | --- | --- |
| URL | 목적지 주소 | `/community` |
| 네비게이션 | 목적지로 이동하는 링크나 메뉴 | 헤더의 게시판 메뉴 |
| 라우터 | 주소에 맞는 화면을 찾아 연결 | `App.jsx`의 Route 설정 |
| 페이지 | 실제로 보여주는 화면 | `CommunityPage.jsx` |

게시판 메뉴 클릭 → URL이 `/community`로 변경 → 라우터가 `CommunityPage`를 선택 → 게시판 화면이 표시되는 순서다. 페이지 파일을 만들기만 해서는 주소와 자동으로 연결되지 않는다.

네비게이션 컴포넌트는 메뉴 표시와 이동을 담당하게 한다. 현재 `Header.jsx`에는 메뉴뿐 아니라 로그아웃, 알림, 알림 모달 처리가 함께 있어 분리할지 검토할 수 있다. 헤더에는 각 기능을 배치하고, 세부 처리는 해당 컴포넌트와 기능 로직에 맡기는 방향이다.

헤더는 다음 구성 요소를 배치한다.

- Navigation: 이동 메뉴
- Notifications: 알림
- AccountMenu: 로그인·로그아웃 버튼

위 구조는 분리 방향을 설명하는 예시이며 아직 구현하지 않았다. 버튼 컴포넌트가 직접 서버 통신을 모두 구현한다는 뜻은 아니고, 인증 처리는 인증 스토어·API 등 기존 역할에 맞게 연결한다.

라우터는 주소와 페이지 연결을 담당한다. 메뉴를 숨겨도 사용자가 URL을 직접 입력할 수 있으므로, 메뉴 표시나 라우팅만으로 서버 접근 권한을 보장하지 않는다.

#### 현재 코드에서 참고할 예

- `front/src/pages/CalculatorInputPage.jsx`: 입력 폼·목록·요약 컴포넌트를 조합하는 페이지 구조.
- `front/src/components/common/Modal.jsx`: 공통 모달의 틀.
- `front/src/components/community/ReportModal.jsx`: 공통 모달에 신고 입력 기능을 구성.
- `front/src/pages/MyPage.jsx`: 페이지 안의 카드·차트 구현을 별도 컴포넌트로 분리할지 검토할 후보. 확정된 오류는 아니다.

### 화면 영역 분리와 그리드 배치

#### 개념

그리드는 화면을 행과 열로 나눠 요소를 배치하는 틀이다. CSS Grid는 이 배치를 구현하는 방법이고, 컴포넌트 분리는 코드의 역할을 나누는 작업이다. 그리드를 사용해도 코드가 자동으로 분리되지는 않는다.

#### 문제

기본정보 입력·수입과 지출 입력·내역 목록·계산 요약을 한 파일에서 모두 구현하면 특정 영역만 수정하기 어렵다.

#### 수정 방향

역할이 분명한 영역을 컴포넌트로 나누고, 페이지에서 그리드 등을 이용해 배치한다.

계산기 페이지는 다음 영역으로 나눈다.

- 왼쪽 영역: 기본정보 입력, 수입·지출 입력, 입력 내역 목록
- 오른쪽 영역: 계산 요약

`CalculatorInputPage.jsx`의 `ProfileForm`, `EntryForm`, `EntryTable`, `SummaryRail` 구성이 참고 예다. CSS의 칸이나 div마다 파일을 만드는 것이 아니라, 기능과 역할이 구분되는 영역을 기준으로 나눈다. 화면 배치가 바뀌어도 기능 컴포넌트를 다시 사용할 수 있도록 한다.

## 2. 미사용 코드와 파일 정리

### 개선 목적

현재 사용하는 구현을 명확히 구분하고, 예전 코드로 인한 혼동을 줄인다.

### 문제

실제 API로 대체된 mock, 예전 구현, 사용하지 않는 파일·함수·변수·import가 남으면 현재 동작하는 코드를 파악하기 어렵다.

### 담당

형상관리자가 통합된 프로젝트를 기준으로 정리 범위와 반영을 관리한다. 다른 팀원 코드의 사용 여부가 불명확하면 담당자에게 확인한다.

### 정리 방향

파일과 함수가 다른 코드에서 실제로 사용되는지, 화면 주소에 연결되어 있는지 살펴본 뒤 불필요한 구현을 정리한다. 메뉴에 보이지 않아도 URL로 접근할 수 있고, 다른 파일을 거쳐 사용되거나 실행 중에 불러오는 코드도 있으므로 단순 검색 결과만으로 삭제 여부를 결정하지 않는다.

mock은 실제 API로 대체되고 해당 화면의 연결까지 완료된 경우 정리한다. 사용 여부나 개발 예정 여부가 불명확한 코드는 담당자에게 확인한다. 삭제할 때는 관련 import와 호출부도 함께 정리하며, 기존 기능이 유지되는지 빌드와 화면 동작으로 검증한다. 변경은 기능별로 나누어 기록하면 문제가 생겼을 때 원인을 찾거나 되돌리기 쉽다.

mock이라는 이유나 파일 이름이 비슷하다는 이유만으로 일괄 삭제하지 않는다. 아직 mock을 사용하는 화면은 실제 API가 연결되기 전까지 유지한다. 검색 결과가 없다는 사실만으로 미사용을 확정하지 않는다.
