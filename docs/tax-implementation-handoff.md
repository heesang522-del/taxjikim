# 세금 계산·집계 작업 이어하기

정리일: 2026-10-22. 집에서는 TJK-168 계산·집계를 진행하고, 학원에서는 ML 분류·재학습 작업을 이어간다.
이 문서는 현재 상태와 다음 작업 안내다. 세금 규칙은 [계산 기준](creator-tax-notes.md), 저장·연결은 [전체 명세](creator-tax-dummy-format.md), ML 상태는 [ML 안내](../ml/docs/home-handoff.md) 한 곳에서 각각 관리한다.

## 가장 최근에 바뀐 순서

```text
PDF 업로드 → 추출·분류 거래를 DB에 최초 저장 → 기존 목록에 표시
→ 사용자가 미분류 카테고리를 지정하거나 건너뛰기
→ 결과 버튼 → 지정한 카테고리만 DB 수정
→ 수정 완료 후 해당 분석의 계산 포함 거래를 DB에서 조회
→ 세금 계산·월별/카테고리별 집계 → 결과 화면
```

- 결과 버튼에서 전체 거래를 다시 최초 저장하는 옛 흐름은 사용하지 않는다.
- 카테고리 수정이 끝나기 전에 결과를 조회하지 않는다. 수정 요청은 거래 ID·소유권을 확인하고 날짜·금액을 함께 덮어쓰지 않는다.
- 조회 대상은 이번 분석의 거래다. 같은 회원·연도라는 이유로 과거 업로드까지 합산하지 않는다.
- 사용자 지정 학습 후보는 카테고리 갱신 시 별도 저장하고, 자동 추천 유지·미분류 건너뛰기는 후보에서 제외한다. 재학습은 별도 작업이다.
- 세금·차트·근거 계산은 역할별 메서드로 나눠도 된다. 지연을 측정해 문제없으면 유지하고 중복 순회 제거·단일 SQL 등 최적화를 먼저 강제하지 않는다.
- 비회원 업로드의 임시 소유권·DB 연결과 로그인 후 귀속은 아직 연결 작업이 남아 있다. 결과 조회를 임의로 로그인 전용으로 바꾸지 않는다.

## 받을 거래 데이터

계산·차트에서 사용하는 거래 내용은 6개다. ID·선택 여부·소유권 등은 조회·수정 경계에서 별도로 관리한다.

| 항목 | 사용 목적 |
| --- | --- |
| 날짜 | 월별 집계 |
| 수입/지출 구분 | 수입과 지출 분리 |
| 거래 설명 | 내역 확인·분류 |
| 최종 카테고리 | 사용자 수정 반영, 원형 차트 집계 |
| 세전 수입 | 세금 계산용, 지출에는 없음 |
| 실제 입출금액 | 수입은 받은 금액, 지출은 쓴 금액 |

기부금·기본공제·창업감면은 거래 목록과 별도의 계산 조건으로 받는다.
PDF 열은 `날짜 / 구분 / 거래 설명 / 세전 수입 / 차감 세율 / 실제 입출금액`으로 변경했다.
차감 세율은 원본 보존 정보이며 계산용 거래 6개에 억지로 추가하지 않는다. 현재 금액 필드 `taxDeducted`와 혼용하지 않는다.

## 현재 코드에서 된 것과 안 된 것

`back/src/main/java/com/kh/back/tax/`:

| 파일 | 현재 역할 |
| --- | --- |
| dto/TaxCalculationInputDto.java | 합산된 수입·경비·기부금 인정액·소득공제 총액 4개 |
| dto/TaxBaseResultDto.java | 기부금 반영 전후 금액과 과세표준 |
| service/TaxCalculationService.java | 과세표준 계산 기능 선언 |
| service/TaxCalculationServiceImpl.java | 위 4개 금액으로 과세표준 계산 |
| TaxCalculatorDraft.java | 가상 금액을 넣어 실행하는 예시 main |

거래 목록 입력, DB 조회·카테고리 수정, 총액·월별·카테고리 집계, 기부금 한도, 올해 세율·창업감면, 평균 예상액, 결과 API는 아직 구현하지 않았다.
예시 과세표준 27,000,000원은 최종세액이 아니다. 이 환경에서 Java 실행 검증은 하지 못했다.

현재 업로드 DTO에는 `preTaxIncome`, `taxDeducted`, `actualAmount`, `amount`가 있지만 Mapper는 세전 수입 등을 별도로 저장하지 않는 구조가 남아 있다. DB 기반 계산 전에 담당자와 저장·조회 필드를 맞춰야 한다.
Python 파서도 차감 금액을 읽는 구조가 남아 있어 새 차감 세율 PDF의 정상 처리를 보장하지 않는다. PDF 생성 확인과 서버 분석 성공은 별개다.

## 집에서 이어갈 작업

1. 현재 브랜치·변경 목록을 확인하고 인계 문서와 실제 코드를 대조한다. 공용 DB·기존 업로드·화면은 다른 담당자가 작업 중이므로 임의 변경하지 않는다.
2. `tax` 안에서 거래 입력·집계 결과 DTO를 정한다. 업로드 DTO를 바꾸기보다 필요한 값을 계산 입력으로 매핑하는 방향이다.
3. DB에서 읽은 거래를 입력으로 총액·월별·카테고리 집계 메서드를 작성한다. DB 연결 전에도 가상 거래 목록으로 검증할 수 있다.
4. 계산·집계는 역할별 파일로 나누고, 결과는 세액·산출 근거·차트 자료를 묶어 한 번 반환하는 방향으로 진행한다. 아직 이 전체 결과 구조를 구현한 것은 아니다.
5. 과세표준 다음으로 올해 세율·기부금 한도·창업감면을 계산 기준과 공식 자료에 맞춰 구현한다. 평균 예상액은 우선 단순 방식으로 두고 세부 기간 등은 이후 논의한다.
6. 시뮬레이션은 수입·지출·기부금·창업감면 조건을 바꿔 같은 계산 로직을 사용한다. 기본공제·기본 결과·회원 창업정보는 유지한다.
7. 연결 경로·DTO를 담당자와 맞춘 뒤 기존 서버·화면에 연결한다. 작업한 금액 계산과 분모 0, 미분류, 제외 거래, 수정 전후 총액을 검증한다.

원형 차트는 선택한 실제 거래의 카테고리별 실제 금액을 같은 구분의 총액으로 나눈다. 수입·지출 분모를 섞지 않고 미분류도 포함한다. 총액 0이면 내역 없음으로 표시하며 미래 평균액을 임의 카테고리로 배분하지 않는다. 비율 반올림은 표시 기준이므로 원금액을 바꾸지 않는다.
서비스 메서드 위 설명은 기능 한 줄, 자세한 계산 의도는 Impl 메서드 내부에 한국어로 적는다. DTO·서비스 인터페이스·구현체는 컨벤션에 맞춰 구분하고 불필요하게 세분화하지 않는다.

## PC를 옮길 때

- 이동 전 최신 코드·문서의 커밋·push 여부를 확인하고, 다른 PC에서 시작할 때 최신 코드를 받는다. 이 문서는 커밋·push 실행 요청이 아니다.
- `output/pdf/creator_transactions_100.pdf`는 가상 거래 100건·4페이지 테스트 PDF다. 실제 세율 자료나 ML 학습 정답이 아니다. 파일은 별도로 챙기고 집 PC에 존재하는지 확인한다.
- ML 데이터·모델·가상환경은 Git 제외 대상이다. 학원 PC 자료가 Git만으로 집에 복사된다고 가정하지 않는다. 집에서 ML 자료를 재생성·재학습할 필요는 없다.
- 마지막 확인한 TJK-168 초안 커밋은 `10fed4f`다. 문서 갱신의 커밋·push와 다른 작업의 최신 여부는 실제 상태로 확인한다.

집에서 새 대화에 붙일 문장:

> `docs/tax-implementation-handoff.md`와 연결된 설계 문서, `tax` 패키지를 읽고 TJK-168을 이어가자. 업로드 때 DB 최초 저장, 결과 버튼에서 지정 카테고리만 수정한 뒤 DB 거래로 계산하는 방향이야. 현재 구현과 문서를 먼저 대조하고 다음 단계를 설명해줘. 기존 업로드·화면·공용 DB는 다른 사람이 작업 중이니 건드리지 말고 계산·집계부터 진행하자.
