## 1. PR이란?

PR(Pull Request)은 **개인 브랜치의 변경을 다른 브랜치에 합쳐 달라는 요청**이다.

| 단계 | 의미 |
| --- | --- |
| Push | 작업한 커밋을 GitHub의 개인 브랜치에 올린다. |
| PR 생성 | 개인 브랜치의 변경을 `develop` 등에 합쳐 달라고 요청한다. |
| 승인(Approve) | 검토자가 내용을 확인하고 반영해도 된다고 표시한다. |
| Merge | 변경을 대상 브랜치에 실제로 합친다. |

**PR 생성과 승인만으로는 코드가 반영되지 않는다. Merge가 끝나야 반영된다.**

## 2. 우리 팀의 승인 기준

- 조원이 작성한 PR은 **김희상의 승인**을 받은 뒤 Merge한다.
- 김희상이 작성한 PR은 **다른 조원 최소 1명의 승인**을 받은 뒤 Merge한다.
- 다른 조원끼리 승인한 것만으로 조원의 PR을 Merge하지 않는다.
- `develop`과 `main`의 PR Merge는 기본적으로 형상관리자 김희상이 수행하되, 위 승인 기준을 충족한 뒤에는 해당 작업 담당자도 수행할 수 있다.
- GitHub는 작성자 외 1명의 승인을 요구한다. 승인 담당자의 구분은 팀 규칙으로 준수한다.

## 3. PR 생성 전 준비

1. 해당 TJK 티켓의 작업을 완료하고 커밋한다.
2. 최신 `develop`을 개인 브랜치에 반영한다.
3. 충돌이 있으면 해결한다.
4. 변경한 기능과 영향을 받는 기존 기능을 실행 확인한다.
5. 개인 브랜치에 push한다.

아래 `{개인명}`은 본인의 브랜치명으로 바꾼다. 진행 중인 변경을 커밋한 상태에서 실행한다.

```
git switch feature/{개인명}
git fetch origin
git merge origin/develop
```

충돌 해결과 실행 확인을 마친 뒤 push한다.

```
git push -u origin feature/{개인명}
```

`develop`과 `main`에 직접 push하지 않는다.

## 4. GitHub에서 PR 생성하기

### ① PR 생성 화면 열기

GitHub 저장소에서 다음 순서로 이동한다.

**Pull requests → New pull request**

### ② 보내는 브랜치와 받는 브랜치 선택

일반 기능 개발 및 일반 수정은 다음과 같이 선택한다.

| 항목 | 선택 | 의미 |
| --- | --- | --- |
| **base** | `develop` | 변경을 받을 브랜치 |
| **compare** | `feature/{개인명}` | 작업한 변경이 있는 브랜치 |

**예시**

```
base: develop ← compare: feature/heesang
```

이 선택은 “feature/heesang의 변경을 develop에 합쳐 달라”는 뜻이다.

### ③ 변경 내용 확인

화면에 표시된 커밋과 변경 파일을 확인한다.

- 해당 TJK 티켓의 변경만 포함되어 있는가?
- 의도하지 않은 파일이 포함되지 않았는가?
- 비밀번호, 토큰 등 비밀 정보가 포함되지 않았는가?

확인이 끝나면 **Create pull request**를 누른다.

### ④ 제목과 본문 작성

아래 작성 형식에 따라 입력하고 **Create pull request**로 요청을 생성한다.

검토 준비가 끝난 작업은 일반 PR로 생성한다.

## 5. PR 작성 형식

### 제목

```
[TJK-번호] 작업 내용
```

**예시**

```
[TJK-2] 로그인 기능 구현
[TJK-3] 게시글 검색 오류 수정
```

### 본문 양식

아래 내용을 복사하여 작성한다. 해당하지 않는 항목은 `없음`으로 적는다.

```
## 관련 티켓
- TJK 번호:
- 티켓 링크:

## 작업 내용
-
-

## 실행 확인
- 확인 방법:
- 확인 결과:

## 영향 및 검토 참고
- 영향을 받는 기존 기능:
- 설정·DB 변경 또는 추가 실행 절차:
- 검토자가 확인할 사항:

## 화면 또는 실행 결과
- 필요한 경우 스크린샷, 로그 또는 영상 첨부
```

### 작성 예시

```
## 관련 티켓
- TJK 번호: TJK-2
- 티켓 링크: 해당 티켓 링크

## 작업 내용
- 아이디와 비밀번호를 사용하는 로그인 기능 구현
- 로그인 실패 시 오류 메시지 표시

## 실행 확인
- 확인 방법:
  1. 정상 계정으로 로그인
  2. 잘못된 비밀번호로 로그인
  3. 로그인 후 기존 게시판 접근
- 확인 결과:
  - 정상 계정 로그인 성공
  - 잘못된 비밀번호 입력 시 오류 메시지 표시
  - 로그인 후 기존 게시판 정상 접근

## 영향 및 검토 참고
- 영향을 받는 기존 기능: 인증 및 게시판 접근
- 설정·DB 변경 또는 추가 실행 절차: 없음
- 검토자가 확인할 사항: 로그인 성공·실패 처리와 인증 설정

## 화면 또는 실행 결과
- 로그인 성공 및 실패 화면 첨부
```

실행 확인 결과는 실제로 확인한 내용을 적는다. 확인하지 못한 항목은 확인하지 못했다고 명시한다.

## 6. 검토 요청하기

PR 생성 후 김희상에게 이메일로 검토를 요청한다.

**이메일 제목**

```
[PR 검토 요청][TJK-번호] 작업 내용
```

**이메일에 포함할 내용**

- PR 링크
- TJK 티켓 번호 또는 티켓 링크
- 작업 내용 한 줄 요약
- 검토 시 특별히 확인할 사항이 있다면 함께 작성

김희상이 작성한 PR은 다른 조원에게 검토를 요청한다.

## 7. PR 검토 및 승인하기

검토자는 다음 순서로 확인한다.

1. PR 본문과 연결된 티켓에서 작업 목적을 확인한다.
2. **Files changed**에서 변경 파일과 코드를 확인한다.
3. 작성된 실행 확인 방법과 결과를 검토하고, 필요한 경우 직접 실행한다.
4. **Review changes**에서 검토 결과를 선택한다.

| 검토 결과 | 의미 |
| --- | --- |
| **Comment** | 질문이나 의견을 남긴다. 승인으로 계산되지 않는다. |
| **Approve** | 검토를 마쳤고 반영해도 된다는 승인이다. |
| **Request changes** | 반영 전에 수정이 필요하다는 요청이다. |

PR 작성자는 자신의 PR을 승인할 수 없다.

### 수정 요청을 받았을 때

해당 PR의 개인 브랜치에서 수정하고 커밋·push한다.

- 수정 내용은 기존 PR에 자동으로 포함된다.
- PR을 새로 만들 필요는 없다.
- 검토 의견에 수정 내용을 답변하고 다시 검토를 요청한다.
- 코드 검토 대화는 해결 여부를 확인한 뒤 **Resolve conversation**으로 해결 처리한다.

**승인 후 변경을 push하면 기존 승인이 취소되므로 다시 승인받는다. PR 자체가 취소되는 것은 아니다.**

## 8. 승인된 PR Merge하기

Merge 전에 다음 내용을 확인한다.

- 대상 브랜치가 올바른가?
- 팀 규칙에 맞는 검토자의 승인을 받았는가?
- 수정 요청과 코드 검토 대화가 해결되었는가?
- 최신 `develop` 반영과 실행 확인이 끝났는가?

조건을 충족하면:

1. **Merge pull request**를 누른다.
2. **Confirm merge**를 누른다.
3. Merge 완료 표시를 확인한다.

**Squash and merge와 Rebase and merge는 사용하지 않는다.**

개인 브랜치는 재사용하므로 **Delete branch를 누르지 않는다.**

Merge 후에는 최신 `develop`에서 통합 결과를 확인한다. 문제가 없으면 티켓을 완료한다.

진행 중인 변경을 정리한 상태에서 다음 명령으로 통합 코드를 받을 수 있다.

```
git switch develop
git pull --ff-only origin develop
```

## 9. PR 검토 중 다음 티켓 작업하기

PR은 연결된 브랜치의 최신 변경을 따라간다. 같은 개인 브랜치에 다음 작업을 push하면 기존 PR에도 포함된다.

따라서 검토 중 다음 티켓은 임시 브랜치에서 진행한다.

### 예시 상황

- 개인 브랜치: `feature/heesang`
- 검토 중인 PR: TJK-2
- 다음 작업: TJK-3
- 임시 브랜치: `work/heesang/TJK-3`

### ① 임시 브랜치 생성

```
git switch feature/heesang
git switch -c work/heesang/TJK-3
```

### ② 다음 작업 진행

TJK-3의 변경은 임시 브랜치에서 커밋·push한다.

```
git push -u origin work/heesang/TJK-3
```

기존 TJK-2 PR의 수정 요청은 `feature/heesang`에서 처리한다. 브랜치를 이동하기 전에는 진행 중인 변경을 커밋하는 등 정리한다.

### ③ 기존 PR 반영 완료 후 개인 브랜치로 복귀

**기존 PR의 승인·Merge·통합 확인이 끝난 뒤** 진행한다. 임시 브랜치의 작업은 먼저 커밋한다.

```
git switch feature/heesang
git fetch origin
git merge origin/develop
git merge work/heesang/TJK-3
```

충돌이 발생하면 해결하고 관련 기능을 실행 확인한다. 이후 개인 브랜치에 push한다.

```
git push origin feature/heesang
```

### ④ 다음 PR 생성 및 임시 브랜치 정리

`feature/heesang → develop` PR을 생성한다. TJK-3의 변경만 포함되는지 확인한다.

임시 브랜치의 모든 변경이 개인 브랜치에 합쳐지고 확인되면, 형상관리자와 미반영 변경 여부를 확인한 뒤 정리한다.

```
git branch -d work/heesang/TJK-3
git push origin --delete work/heesang/TJK-3
```

로컬 삭제가 거부되면 미반영 커밋을 확인한다. 강제 삭제하지 않는다.

## 10. main으로 보내는 PR

일반 작업은 `develop`으로 보낸다. `main` 대상 PR은 다음 경우에 사용한다.

| 상황 | base | compare |
| --- | --- | --- |
| 회의에서 결정한 배포 반영 | `main` | `develop` |
| 배포 버전의 긴급 오류 수정 | `main` | `hotfix/TJK-{번호}` |
| 긴급 수정을 develop에도 반영 | `develop` | 같은 `hotfix/TJK-{번호}` |

`main` 대상 PR에도 같은 승인 기준을 적용한다. 긴급 수정은 정기 회의를 기다리지 않고 검토를 요청한다.
