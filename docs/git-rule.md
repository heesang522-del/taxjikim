# Git 형상관리 규칙

TJK 티켓을 기준으로 작업하며, 개인별 브랜치에서 개발한다. `develop` 또는 `main`에 변경을 반영하려면 GitHub에서 PR을 생성하고, 형상관리자 김희상에게 이메일로 검토를 요청한다.

형상관리자는 PR의 변경 파일과 코드, 실행 확인 결과를 검토한다. `develop`과 `main`의 PR merge는 기본적으로 형상관리자 김희상이 수행하되, 아래 승인 기준을 충족한 뒤에는 해당 작업 담당자도 수행할 수 있다. 변경은 GitHub의 PR merge로 반영한다.

코드 작성 기준은 GitHub 저장소의 코드 컨벤션을 따른다.

## 1. 브랜치와 커밋

| 브랜치 | 용도 |
| --- | --- |
| `main` | 검증된 배포·안정 버전 |
| `develop` | 완료된 작업 통합 및 실행 확인 |
| `feature/{개인명}` | 개인별 기능 개발 |
| `hotfix/TJK-{번호}` | 배포 버전의 긴급 오류 수정 |
- 티켓 하나는 한 명이 담당하며, 개인별 feature 브랜치는 최신 `develop`에서 생성한다.
- 담당자는 자신의 feature 브랜치에 자유롭게 push할 수 있다.
- 개인별 feature 브랜치에서는 한 번에 하나의 티켓을 작업한다. 이전 작업의 반영 및 통합 확인이 끝난 뒤 최신 `develop`을 반영하고 다음 티켓을 진행한다.
- `main`과 `develop`에는 개인 작업을 직접 작성하거나 강제 push하지 않는다.
- 일반 기능 개발 브랜치에는 개인명을 사용하고, 티켓과 커밋에는 일일 TODO 번호가 아닌 TJK 번호를 사용한다.

커밋 형식: `타입(영역): [TJK-번호] 작업 내용`

| 타입 | 용도 |
| --- | --- |
| `feat` | 기능 추가 |
| `fix` | 버그 수정 |
| `refactor` | 동작을 유지하는 구조 개선 |
| `test` | 테스트 추가·수정 |
| `docs` | 문서 추가·수정 |
| `chore` | 설정·빌드 등 기타 작업 |

```
feat(auth): [TJK-2] 로그인 기능 구현
fix(board): [TJK-3] 게시글 검색 오류 수정
docs(setup): [TJK-1] 프로젝트 실행 방법 작성
```

서로 관련 없는 변경은 커밋을 나눈다. 하나의 티켓에 여러 커밋을 작성할 수 있다.

## 2. 작업 및 반영 절차

```
티켓 생성 → 개인별 feature 브랜치에서 개발·커밋
→ 최신 develop 반영·실행 확인 → 개인 브랜치 push
→ develop 대상 PR 생성 → 김희상 형상관리자에게 검토 요청 이메일 발송
→ PR 검토·승인 → 형상관리자 또는 해당 작업 담당자가 develop 대상 PR merge
→ 통합 확인 → 티켓 완료
```

- 일반 기능 개발 PR의 대상 브랜치는 `develop`으로 한다.
- PR에는 TJK 번호, 변경 내용, 실행 확인 방법 및 결과를 작성한다.
- 검토 요청 이메일에는 PR 링크와 TJK 번호를 포함한다.
- 형상관리자는 변경 파일, 기능 동작, 코드 가독성, 중복, 기존 기능 영향을 검토한다.
- 수정 요청이 있으면 같은 개인 브랜치에서 수정·push하고, PR에서 다시 확인받는다.
- 형상관리자 본인의 작업은 담당자 외 최소 1명의 검토와 승인을 받는다.
- 다른 조원의 작업은 형상관리자 김희상의 승인을 받는다. 다른 조원끼리의 승인만으로 merge하지 않는다.
- PR merge는 기본적으로 형상관리자 김희상이 수행하되, 위 승인 기준을 충족한 뒤에는 해당 작업 담당자도 수행할 수 있다.
- 승인된 작업은 개별 커밋 이력이 유지되는 merge 방식으로 반영한다. Squash merge와 Rebase merge는 사용하지 않는다.
- 한 작업의 통합 확인이 끝난 뒤 다음 작업을 반영한다.
- 통합 중 문제가 생기면 티켓을 완료하지 않고, 수정 후 다시 확인한다.
- `develop → main` 반영은 통합 검증 후 회의에서 별도로 결정한다. 결정 후 `main` 대상 PR을 생성하고, 같은 승인 기준과 merge 담당자 규칙에 따라 반영한다.

## 3. 최신 코드 반영과 충돌 해결

PR 검토를 요청하기 전에 진행 중인 변경을 커밋하고, 최신 `develop`을 자신의 feature 브랜치에 merge한 뒤 관련 기능을 실행한다.

충돌이 발생하면 다른 팀원의 코드를 임의로 삭제하거나 덮어쓰지 않는다. 해결이 불명확하면 해당 코드 담당자와 확인한다.

PR 검토 후 `develop`이 변경되면 merge 전에 다시 반영하고 실행한다. 이 과정에서 기능이 달라졌다면 티켓과 PR에 기록하고 다시 검토받는다.

## 4. 브랜치 유지와 삭제

개인별 feature 브랜치는 티켓이 완료되어도 삭제하지 않고 다음 작업에 재사용한다.

다음 티켓을 시작하기 전에 이전 작업이 `develop`에 반영되고 통합 확인·티켓 완료까지 끝났는지 확인한다. 이후 최신 `develop`을 자신의 feature 브랜치에 반영한다.

```
git switch feature/{개인명}
git fetch origin
git merge origin/develop
git push origin feature/{개인명}
```

개인별 feature 브랜치를 더 이상 사용하지 않을 때는 미반영 변경이 없는지 확인한 뒤 형상관리자가 GitHub 브랜치를 삭제한다. 각자의 로컬 브랜치는 각자가 정리한다.

로컬 삭제가 거부되면 미반영 커밋이 있는지 형상관리자와 확인한다. 강제 삭제하지 않는다. merge로 반영된 코드와 커밋 이력은 `develop`에 남는다.

## 5. 긴급 수정 절차

`main`에 반영된 배포 버전에서 로그인 불가 등 서비스 이용에 큰 영향을 주는 오류가 발생하면, 발견한 즉시 긴급 수정 여부를 판단한다.

`develop`에서 발견한 오류는 일반 수정으로 처리한다. 담당자는 자신의 개인별 feature 브랜치에서 수정하고, `develop` 대상 PR을 생성하여 형상관리자에게 이메일로 검토를 요청한다.

긴급 수정은 다음 절차를 따른다.

```
배포 버전 오류 공유·TJK 티켓 생성
→ 최신 main에서 hotfix/TJK-{번호} 생성
→ 수정·실행 확인·push
→ main 대상 PR 생성
→ 김희상 형상관리자에게 PR 링크를 이메일로 보내 긴급 검토 요청
→ PR 검토·승인
→ 형상관리자 또는 해당 작업 담당자가 main 대상 PR merge → 배포
→ 같은 hotfix에서 develop 대상 PR 생성
→ PR 검토·승인 → 형상관리자 또는 해당 작업 담당자가 develop 대상 PR merge
→ 배포 결과·통합 확인
→ 티켓 완료·hotfix 삭제
```

- 긴급 검토는 정기 회의를 기다리지 않고 진행한다.
- hotfix에는 해당 오류 해결에 필요한 변경만 포함한다.
- 형상관리자 본인의 긴급 수정도 담당자 외 최소 1명의 검토와 승인을 받는다.
- 긴급 수정에도 일반 작업과 같은 승인 기준과 merge 담당자 규칙을 적용한다.
- 형상관리자는 `main`과 `develop` 모두에 수정이 반영됐는지 확인한다.
- 두 브랜치의 반영 및 확인이 끝난 뒤 hotfix를 삭제한다.
