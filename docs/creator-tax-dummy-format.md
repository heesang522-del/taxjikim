# 거래 분류·저장·세금 결과 연결 명세

정리일: 2026-10-22. 목표 설계이며 구현 완료를 뜻하지 않는다. 세금 계산·공제·창업정보 입력은 [예상세액 계산 기준](creator-tax-notes.md)을 따른다. PDF·금액·ID는 가상 연결 검증 예시다.

## 1. 전체 과정과 담당 작업

```text
더미 원본·정답 제작 → 원본으로 PDF 한 개 생성 → 사용자 PDF 업로드
→ Spring 기본정보·거래 추출 → 수입·지출을 구분해 FastAPI에 전달
→ ML 카테고리 분류 → Spring에서 원본과 연결
→ 추출·분류한 거래를 업로드 시 DB에 최초 저장
→ React의 기존 거래 목록에 표시 → 사용자가 미분류 카테고리 지정 또는 건너뛰기
→ 결과 버튼 클릭 → 사용자가 지정한 카테고리만 DB 수정·재학습 후보 구분
→ 수정 완료 후 해당 분석의 DB 거래 조회 → 계산·집계 → 결과 화면 표시
→ 별도 재학습 작업에서 후보 검토·학습·평가
```

- 모델: 수입용과 지출용 모델을 따로 학습·평가·저장한다. 각 모델에서 TF-IDF + LogisticRegression / TF-IDF + LinearSVC를 동일 자료로 비교 후 선정한다. 거래 구분(INCOME/EXPENSE)은 모델 선택에 사용하고, 각 분류기의 입력 특징은 설명 하나로 유지한다.
- 모델 입력은 거래 설명(description) 하나다. 거래처는 요구하거나 모델에 전달하지 않는다. 더미 설명은 품목·서비스·용도가 드러나도록 작성한다. 실제 원문이 모호하면 내용을 임의로 보충하지 않고 미분류를 허용한다. PDF에 정답 카테고리를 넣지 않는다.
- PDF·CSV·Excel 입력을 공통 거래 구조로 맞추는 방향이다. 모든 입력을 중간 CSV 파일로 만들 필요는 없다. Spring은 수입·지출별 설명과 연결용 순번을 JSON으로 전달하고, 금액·날짜 원본은 유지한다. 입력 형식별 추출·검증 지원은 별도 구현 사항이다.
- 수입도 별도 ML 모델로 유튜브 플랫폼 정산·광고·협찬·외부 후원·기타를 분류하고, 정보가 부족하면 미분류로 처리한다. 수입 규칙 분류를 우선한다는 이전 계획을 대체한다. AD_SPONSORSHIP은 광고·협찬을 합친 하나의 카테고리다.
- 카테고리는 시각화용이며 경비 인정 여부·원천징수 세율을 판단하지 않는다.
- 미래 수입·지출은 우선 평균 방식으로 처리한다. 세부 예측은 분류 모델과 별개다.

## 2. 더미데이터와 PDF 형식

### 분류 데이터

버전별 상태·재현·다음 단계는 [ML 작업 안내](../ml/docs/home-handoff.md), 파일·코드 뜻은 [ML 파일 안내](../ml/docs/file-guide.md)에서 관리한다.
여행·먹방·게임·일상·리뷰 표현을 포함하되 분야명·접미사만 바꾼 문장을 독립 거래 유형으로 과장하지 않는다. 수입 데이터는 지출 이후 진행한다.

#### 콘텐츠 분야 거래의 범주 적용 — 사용자 합의

새 카테고리를 추가하지 않고 기존 영문 코드와 화면 표시명을 유지한다.

| 거래 내용 | 적용 코드 | 범위 |
| --- | --- | --- |
| 촬영용 음식·식재료 | SUPPLIES_PROPS | 기존 소모품·소품에 포함 |
| 촬영 출장 숙박 | SPACE_RENTAL | 기존 공간 대여에 포함 |
| 게임 구매·이용권 | SOFTWARE_LICENSE | 기존 소프트웨어에 포함 |
| 리뷰용 전자기기 | EQUIPMENT | 리뷰 목적이어도 하드웨어로 분류 |

소모품·소품의 기존 색지·테이프·장식물·청소용 티슈, 공간 대여의 기존 스튜디오·녹음 부스·촬영용 주방·회의실 대관도 유지한다. 음식·숙박을 위 범주에 포함하는 것은 서비스 통계·분류를 위한 합의이며 세법상 경비 인정 판정이 아니다. 실제 설명에 없는 촬영·업무 목적을 임의로 덧붙이지 않는다. `물품 구매`처럼 판단 근거가 부족하면 미분류를 허용한다.

| 자료 | 용도 | PDF 포함 |
| --- | --- | --- |
| 기본정보·날짜별 거래 | PDF 생성·추출 대조 | 포함 |
| 거래별 정답 카테고리·근거 | 학습·평가 | 제외 |
| 반복 구독·할부·일회성 설정 | 생성 검수·후속 예측 검토 | 제외 |
| 학습·검증·시험 분할 | 모델 비교 | 제외 |

아래 6건은 연결 검증용이다. 이후 월별 유튜브 정산·비정기 협찬·구독·할부·일회성 구매가 섞인 올해 기준일까지의 업무 거래로 확대한다. 모델 학습자료는 여러 거래 표현으로 별도 확대하고 같은 문장 틀을 학습·시험에 중복 배치하지 않는다. 규모는 미정이다.

### PDF 상단 기본정보

| 항목 | 예시 |
| --- | --- |
| 연도 / 자료 기간 | 2026 / 2026-01-01~2026-09-30 |
| 관측 기준일 | 2026-09-30 |
| 사업자 유형 / 등록 여부 | 면세 1인 유튜버 / 등록 |
| 기본공제액 | 3,000,000원 — 본인 포함 총액 |
| 기본공제 설명 | 본인 1명과 공제 요건을 충족하는 부양가족 1명의 기본공제 |
| 창업감면 전제 | 대상 요건을 충족한다고 가정한 시뮬레이션 |

위 공제 총액은 예시다. 실제 서비스는 본인 기본공제와 추가 적용할 공제 정보를 받으며 본인 공제를 중복 가산하지 않는다. 창업감면 확인·창업일·사업장 지역·회원 정보 저장은 예상세액 계산 기준을 따른다. 이 연결 예시에서 감면 계산은 하지 않는다.

### PDF 거래 표

| 날짜 | 구분 | 거래 설명 | 세전 수입 | 차감 세율 | 실제 입출금액 |
| --- | --- | --- | ---: | ---: | ---: |
| 2026-03-05 | 수입 | 유튜브 정산 | 1,000,000 | 4.1% | 959,000 |
| 2026-03-08 | 수입 | 광고 협찬 정산 | 1,000,000 | 3.3% | 967,000 |
| 2026-03-10 | 지출 | 영상 편집 프로그램 월 이용료 | — | — | 35,000 |
| 2026-03-12 | 지출 | 촬영용 카메라 할부 2회차 출금 | — | — | 300,000 |
| 2026-03-13 | 지출 | 촬영 장소 이동 택시비 | — | — | 24,000 |
| 2026-03-15 | 지출 | 물품 구매 | — | — | 50,000 |

- 원화 예시다. 차감 세율 4.1%·3.3%는 테스트용 예시값이며 플랫폼별 실제 세율을 뜻하지 않는다. 예시에서는 다른 차감 없이 세전 수입 × (1 - 차감 세율)로 실제 입금액을 맞췄다. 미확인은 빈 값으로 두고 0%와 구분하며 실제 자료의 입출금액을 임의로 덮어쓰지 않는다.
- 업무에 이미 사용한 지출을 전제로 한다. 일시불은 실제 출금 전액, 할부는 회차 출금액만 넣는다. 업무 출금 전액을 당해 경비로 반영하는 프로젝트 단순화 가정은 결과에 안내한다.
- 시스템 ID·카테고리 정답은 PDF에 표시하지 않는다. 추출 시 거래 순번 itemIndex를 1부터 부여한다.
- 이 발췌로 다른 달의 거래가 0원이거나 연간 수입이 확정됐다고 판단하지 않는다.

## 3. PDF 추출 → 머신러닝 전달 형식

### Spring 추출 데이터

기본정보는 거래와 분리한다. 기본정보 필드는 taxYear, periodStart, asOfDate, businessType, businessRegistered, basicDeductionAmount, basicDeductionReason, startupReliefAssumedEligible로 제안한다.

거래 예시:

```json
{
  "itemIndex": 3,
  "transactionDate": "2026-03-10",
  "transactionType": "EXPENSE",
  "description": "영상 편집 프로그램 월 이용료",
  "amount": 35000,
  "preTaxIncome": null,
  "deductedTaxRate": null
}
```

amount는 실제 입출금액이다. 카테고리가 없다고 행을 제외하지 않는다. 금액·날짜 추출 오류와 카테고리 미분류는 서로 다른 상태다.

PDF 열은 차감 **금액**에서 차감 **세율**로 변경했다. `deductedTaxRate`는 목표 명세의 제안 이름이며 4.1%는 숫자 4.1로 전달하는 제안 기준이다. 현재 코드의 `taxDeducted`는 금액 필드이므로 여기에 세율을 그대로 넣지 않는다. 파서·DTO·DB 변경은 담당자와 맞춰야 하며 이 문서 수정으로 구현되지는 않는다.

계산·집계에 전달할 거래는 날짜, 수입/지출 구분, 설명, 최종 카테고리, 세전 수입, 실제 입출금액의 6개 값으로 구성한다. 차감 세율은 업로드 원본 정보로 별도 보존하고 연간 예상세액 계산의 최종 세율로 사용하지 않는다. 거래 ID·분석 ID는 DB 조회·수정 연결용으로 별도 유지한다.

### Spring → FastAPI 요청

```json
{
  "transactionType": "EXPENSE",
  "items": [
    {"itemIndex": 3, "description": "영상 편집 프로그램 월 이용료"},
    {"itemIndex": 4, "description": "촬영용 카메라 할부 2회차 출금"},
    {"itemIndex": 5, "description": "촬영 장소 이동 택시비"},
    {"itemIndex": 6, "description": "물품 구매"}
  ]
}
```

위는 지출 모델 요청 예시다. 수입 2건은 transactionType=INCOME으로 별도 요청하며 수입 모델을 사용한다. itemIndex는 연결용이며 모델 특징에 넣지 않는다. ID·정답·정답 근거·분할 정보도 모델 특징에서 제외한다. 실제 API 경로는 구현 시 정한다.

### FastAPI → Spring 기대 응답

```json
{
  "modelVersion": "category-v1-example",
  "predictions": [
    {"itemIndex": 3, "categoryCode": "SOFTWARE_LICENSE", "reviewRequired": false},
    {"itemIndex": 4, "categoryCode": "EQUIPMENT", "reviewRequired": false},
    {"itemIndex": 5, "categoryCode": "TRANSPORT", "reviewRequired": false},
    {"itemIndex": 6, "categoryCode": "UNCLASSIFIED", "reviewRequired": true}
  ]
}
```

위 응답은 목표 출력이며 실제 측정 결과가 아니다. 버전명도 예시다. 미분류 점수·임계값은 검증자료로 정한다. 응답 순서가 아니라 itemIndex로 연결하고 누락을 검사한다. 6번처럼 품목을 알 수 없는 거래는 별도 needs_info 검증자료로 관리하고 특정 용도의 정답을 억지로 붙이지 않는다.

2026-10-21 사용자 합의: 내부 처리·API·DB·학습 정답은 위 영문 코드를 사용하고, React 화면에서만 한글 표시명으로 변환한다. 기존 프론트·DB 값과의 대조 및 필요한 매핑은 구현 전에 확인한다. 기타 거래를 검토해 새 카테고리를 추가할 수 있으며, 추가 시 선택지·저장값·학습 정답·모델 지원 범위를 함께 맞춘다.

## 4. DB 저장 형식

### 기존 테이블 확장 제안

현재 Mapper에서 아래 3개 테이블 사용을 확인했다. 실물 DDL은 미확인이므로 기존 스키마와 대조해 확장하고 같은 테이블을 중복 생성하지 않는다.

| 테이블 | 저장 필드 |
| --- | --- |
| FILE_META | 기존 파일 정보·소유자 + 파일 해시·분석 입력 연결·처리 상태 |
| TAX_INPUTS | taxInputId, userId, taxYear, periodStart, asOfDate, businessType, businessRegistered, basicDeductionAmount, basicDeductionReason, startupReliefAssumedEligible |
| TAX_TRANSACTIONS | transactionId, taxInputId, userId, sourceFileId, sourceItemIndex, transactionDate, transactionType, description, amount, preTaxIncome, deductedTaxRate, predictedCategoryCode, categoryCode, categorySource, extractionStatus, classificationStatus, modelVersion, isEdited |

학습 후보는 거래와 별도인 DB 테이블에 저장한다. 원본 거래 ID, 설명, 사용자 지정 카테고리, 학습 반영 상태를 관리하며 실제 테이블명·컬럼명은 구현 시 정한다. 모델 입력은 설명만 사용하고 ID·상태는 제외한다.

기본공제는 TAX_INPUTS에 저장하고 일반 지출로 저장하지 않는다. 금액은 원 단위 정수(BIGINT 또는 DECIMAL 소수점 0), 날짜는 DATE, ID는 기존 자동 증가 숫자 형식과 맞춘다. SQL 열 이름은 기존 규칙에 맞춰 매핑하고 API는 camelCase·JSON 숫자를 사용한다. null과 0을 구분한다.

### 6건 저장 예시

공통 가상 ID: taxInputId=501, sourceFileId=301, userId=42. 사용자 ID는 인증 정보로 정한다.

| 원본 순번 | type | amount | preTaxIncome | deductedTaxRate (%) | categoryCode | categorySource |
| ---: | --- | ---: | ---: | ---: | --- | --- |
| 1 | INCOME | 959000 | 1000000 | 4.1 | YOUTUBE_SETTLEMENT | MODEL |
| 2 | INCOME | 967000 | 1000000 | 3.3 | AD_SPONSORSHIP | MODEL |
| 3 | EXPENSE | 35000 | null | null | SOFTWARE_LICENSE | MODEL |
| 4 | EXPENSE | 300000 | null | null | EQUIPMENT | MODEL |
| 5 | EXPENSE | 24000 | null | null | TRANSPORT | MODEL |
| 6 | EXPENSE | 50000 | null | null | UNCLASSIFIED | UNCLASSIFIED |

- predictedCategoryCode는 ML 추천을 보존한다. modelVersion은 해당 수입·지출 모델의 버전을 기록한다.
- 날짜·금액이 정상인 6건의 extractionStatus는 VALID다. 6번만 classificationStatus=NEEDS_REVIEW, 나머지는 CLASSIFIED다.
- 6번을 사용자가 소모품·소품으로 변경하면 categoryCode=SUPPLIES_PROPS, categorySource=USER, isEdited=true, classificationStatus=USER_CONFIRMED로 갱신한다. 원문·금액·원래 ML 추천 UNCLASSIFIED는 보존한다. 재추론으로 사용자 값을 덮어쓰지 않는다.
- 차감 세금을 실제 세액공제 계산에 활용한다면 국내 소득세·지방세·외국세 등을 상세 구분해야 한다. 이번 추가 납부·환급 계산에는 사용하지 않는다.

### 저장 순서·실패·중복 (2026-10-22 갱신)

1. PDF 업로드 처리에서 추출·분류한 거래와 출처를 DB에 최초 저장한다. 카테고리가 미분류여도 거래를 보존한다. 추출 실패 상태와 정상 거래는 구분한다.
2. 저장된 거래를 기존 목록에 표시한다. 사용자는 미분류 카테고리를 지정하거나 건너뛴다. 결과 버튼 전의 카테고리 선택은 화면에서 유지한다. ML 실패 시 원본과 실패 상태를 보존한다.
3. 결과 버튼을 누르면 지정한 거래의 카테고리와 관련 수정 상태만 DB에서 갱신한다. 전체 거래를 다시 INSERT하거나 날짜·금액을 함께 덮어쓰지 않는다. 사용자 지정 학습 후보 저장은 이 갱신과 함께 처리하고, 자동 추천 유지·미분류 건너뛰기는 후보에서 제외한다. 버튼에서 즉시 재학습하지 않는다.
4. sourceFileId+sourceItemIndex로 같은 행의 재시도 중복을 막는다. 현재 일반 INSERT에도 출처 연결을 추가해야 한다.
5. 불필요한 재집계 통합·중복 검사 최적화를 먼저 강제하지 않는다. 실제 지연을 측정하고 문제없으면 단순한 구현을 유지한다. 재시도에 의한 중복 저장 방지와 소유권 검사는 별개로 유지한다. 다른 파일의 거래를 금액·날짜가 같다는 이유만으로 삭제하지 않는다.
6. 수정 요청은 분석 입력의 소유권을 검증한다. 동일 연도라도 분석 입력 ID로 구분하고 기존 결과를 무조건 덮어쓰지 않는다.

7. 카테고리 갱신이 완료된 뒤 해당 분석의 계산 포함 거래를 DB에서 조회해 계산·집계하고 결과를 반환한다. 수정 실패 시 변경된 것처럼 결과로 이동하지 않는다. 이전 업로드를 회원·연도만으로 모두 합산하지 않는다.

파일은 공개 업로드 경로에 두지 않는다. 비로그인 결과 조회 요구와 업로드 시 DB 저장을 연결할 임시 소유권·계정 귀속 방식은 아직 연결 설계가 필요하다. 이를 해결하려고 결과 버튼에 새 로그인 요구를 임의로 추가하지 않는다.

### 사용자 지정 데이터와 재학습

| 최종 거래 상태 | 결과 버튼 클릭 시 DB 처리 | 재학습 후보 |
| --- | --- | --- |
| 사용자가 카테고리를 직접 지정 | 기존 거래의 카테고리 갱신 | 예 — 검토 후 사용 |
| 자동 추천 카테고리를 그대로 유지 | 업로드 시 저장한 값 유지 | 아니오 |
| 미분류를 건너뛰거나 그대로 유지 | 저장된 UNCLASSIFIED 유지 | 아니오 |

- 모델 추천은 predictedCategoryCode, 최종 선택은 categoryCode로 분리한다. categorySource=USER 등 카테고리 지정 사실로 후보를 판별한다. 금액·설명만 수정한 isEdited=true 거래를 사용자 정답으로 간주하지 않는다.
- 사용자 지정이 있어도 세금계산 버튼을 누르기 전에는 확정된 재학습 후보로 넣지 않는다. 사용자가 UNCLASSIFIED를 선택한 경우도 학습 정답에서 제외한다.
- 사용자 지정값은 검토할 학습 후보이며 무조건 정확한 정답으로 단정하지 않는다. 수입·지출 후보를 구분해 각각 해당 모델 재학습에 사용한다. 후보에 거래 구분을 보존하고 서로 다른 모델의 정답 범주를 섞지 않는다.
- 설명이 `물품 구매`처럼 모호하면 사용자가 카테고리를 지정했더라도 해당 설명을 특정 카테고리의 학습 정답으로 사용하지 않는다. 거래 저장과 세금 계산은 허용하고, 후보 검토에서 학습 제외로 처리한다. 사용자에게 설명 보완을 강제하지 않는다.
- 사용자가 실제 내용을 바탕으로 설명을 구체화한 경우에는 설명과 지정 카테고리가 일치하는지 검토 후 학습에 사용한다. 초기 버전은 사람이 후보를 검토·승인하고 수동으로 재학습한다. 설명의 충분함을 완벽하게 자동 판별하는 기능은 초기 범위에 포함하지 않는다.
- 더미데이터의 모호한 설명은 특정 지출 카테고리를 억지로 부여하지 않고 별도 미분류 검증 자료로 관리한다.
- 별도 재학습 작업에서 후보를 검토·중복 제거한 뒤 학습한다. 스케줄러 자동화는 수동 재학습·평가 확인 후 진행하며, 자동 실행 시점·주기는 미정이다. 평가 자료는 학습에 섞지 않고 새 모델 평가 후 교체 여부를 정한다.

## 6. 결과 화면 연결 및 기대값

| 결과 영역 | 기준 | 6건의 기대값 |
| --- | --- | --- |
| 수입·지출 요약 | 실제 입출금 | 수입 1,926,000원 / 지출 409,000원 / 차액 1,517,000원 |
| 세금 계산용 수입 | 세전 금액 | 2,000,000원 |
| 월별 차트 | 거래 날짜·실제 금액 | 3월 수입 1,926,000원 / 지출 409,000원 |
| 수입 출처 차트 | 실제 입금 기준 명시 | 유튜브 959,000원 / 광고·협찬 967,000원 |
| 지출 카테고리 차트 | 실제 출금 | 소프트웨어 35,000원 / 장비 300,000원 / 교통 24,000원 / 미분류 50,000원 |
| 산출 근거 기본공제 | PDF 기본정보 | 3,000,000원과 공제 설명 |

세전 기준 차트를 추가한다면 제목·범례로 구분한다. 예시 차감액 합계는 74,000원이며 새 수입·지출로 다시 더하지 않는다. 6번을 소모품·소품으로 수정하면 해당 차트 항목만 이동하고 총지출은 409,000원 그대로다.

최종 연간 세액은 전체 자료·미래 예측·해당 연도 세법·감면 확인 후 계산한다. 이 발췌에서 임의로 연간 세액을 만들지 않는다. 연간 결과에서는 실제/예상을 분리하고 세전 수입→경비→기부 인정액→기본공제와 사유→과세표준→산출세액→감면·세액공제→최종 예상세액을 보여준다. 추가 납부·환급액은 표시하지 않는다.

결과 조회는 비로그인도 가능하다. 결과 저장은 가입·로그인 후 원래 결과를 유지해 DB에 저장한다. 시뮬레이션은 로그인 사용자만 진입·계산·비교·저장 가능하다. 시뮬레이션 입력은 추가 세전 수입·업무 지출·적격 복지단체 기부·창업감면 조건이며 기준/변경 세액과 차이·기부 인정액·감면액을 표시한다. 노란우산 계산식을 이름만 바꿔 사용하지 않는다.

### 시뮬레이션의 창업감면 조건 (2026-10-22 확정)

- 기본 계산의 감면 적용 여부·창업일·창업 사업장 지역을 불러와 시나리오에서 변경할 수 있게 한다. 기본공제는 기본 계산의 값을 유지한다.
- 기본 결과와 시뮬레이션은 같은 계산 로직을 사용하며 변경 조건에 맞는 감면을 다시 계산한다. 자격을 자동 확정한 결과가 아니라 가정에 따른 비교임을 표시한다.
- 기본 결과·회원의 저장된 창업정보는 그대로 유지하고, 시나리오 저장 시 변경한 감면 조건과 결과를 함께 저장한다. 초기화하면 기본 조건으로 복원한다.
- 비교 화면에 감면 적용 여부·감면액과 최종 예상세액의 차이를 보여준다. 실제 감면율·기간·대상 업종 확인은 계산 구현에 포함한다.
