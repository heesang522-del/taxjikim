# 더미 PDF → 머신러닝 분류 → 화면 → DB 저장 인계 명세

작성일: 2026-10-19. **이 파일 하나를 구현 담당자에게 전달한다.** 아래는 앞으로 구현할 형식과 기대 결과다. 현재 구현 완료를 뜻하지 않는다. 모든 거래·금액·ID는 가상 예시다.

## 1. 전체 과정과 담당 작업

```text
더미 원본·정답 제작 → 원본으로 PDF 한 개 생성 → 사용자 PDF 업로드
→ Spring 기본정보·거래 추출 → 지출을 FastAPI에 전달
→ ML 카테고리 분류 → Spring에서 원본과 연결·DB 저장
→ React에 기본정보·수입·지출·미분류 표시 → 수정 시 DB 갱신
```

- 모델: TF-IDF + LogisticRegression / TF-IDF + LinearSVC를 동일 자료로 비교 후 선정한다.
- 모델 입력은 거래처·설명이다. PDF에 정답 카테고리를 넣지 않는다.
- 수입은 유튜브 정산·광고 협찬으로 표시한다. 첫 구현에서는 아래 명확한 수입 설명을 규칙으로 구분한다. 수입까지 ML로 분류하는 것은 별도 범위다.
- 카테고리는 시각화용이며 경비 인정 여부·원천징수 세율을 판단하지 않는다.
- 미래 수입·지출 예측은 별도이며 방식 미정이다. 개발 시작 전 반드시 결정한다.

## 2. 더미데이터와 PDF 형식

### 제작할 자료

| 자료 | 용도 | PDF 포함 |
| --- | --- | --- |
| 기본정보·날짜별 거래 | PDF 생성·추출 대조 | 포함 |
| 거래별 정답 카테고리·근거 | 학습·평가 | 제외 |
| 반복 구독·할부·일회성 설정 | 생성 검수·후속 예측 검토 | 제외 |
| 학습·검증·시험 분할 | 모델 비교 | 제외 |

아래 6건은 연결 검증용이다. 이후 월별 유튜브 정산·비정기 협찬·구독·할부·일회성 구매가 섞인 올해 기준일까지의 업무 거래로 확대한다. 모델 학습자료는 여러 거래 표현으로 별도 확대하고 같은 문장 틀을 학습·시험에 중복 배치하지 않는다. 규모는 미정이다.

### PDF 상단 기본정보

| 항목 | 예시 |
| --- | --- |
| 연도 / 자료 기간 | 2026 / 2026-01-01~2026-09-30 |
| 관측 기준일 | 2026-09-30 |
| 사업자 유형 / 등록 여부 | 면세 1인 유튜버 / 등록 |
| 기본공제액 | 3,000,000원 — 본인 포함 총액 |
| 기본공제 설명 | 본인 1명과 공제 요건을 충족하는 부양가족 1명의 기본공제 |
| 창업감면 전제 | 대상 요건을 충족한다고 가정한 시뮬레이션 |

가족 수를 추가 질문하거나 본인 공제를 다시 더하지 않는다. 감면 계산용 창업일·창업 당시 나이·사업장 지역은 법규 확인 후 일관된 가상값으로 추가한다. 이 연결 예시에서 감면 계산은 하지 않는다.

| --- | --- | --- | --- | ---: | ---: | ---: |

- 원화 예시다. 차감 세금은 자료에 있는 가상값이며 고정 세율로 역산하는 규칙이 아니다. 미확인은 빈 값으로 두고 0원과 구분한다.
- 업무에 이미 사용한 지출을 전제로 한다. 일시불은 실제 출금 전액, 할부는 회차 출금액만 넣는다. 업무 출금 전액을 당해 경비로 반영하는 프로젝트 단순화 가정은 결과에 안내한다.
- 시스템 ID·카테고리 정답은 PDF에 표시하지 않는다. 추출 시 거래 순번 itemIndex를 1부터 부여한다.
- 이 발췌로 다른 달의 거래가 0원이거나 연간 수입이 확정됐다고 판단하지 않는다.

## 3. PDF 추출 → 머신러닝 전달 형식

### Spring 추출 데이터

기본정보는 거래와 분리한다. 기본정보 필드는 taxYear, periodStart, asOfDate, businessType, businessRegistered, basicDeductionAmount, basicDeductionReason, startupReliefAssumedEligible로 제안한다.

거래 예시:

```json
{
  "itemIndex": 3,
  "transactionDate": "2026-03-10",
  "transactionType": "EXPENSE",
  "counterparty": "가상편집도구",
  "description": "정기 결제",
  "amount": 35000,
  "grossIncome": null,
  "withheldTaxAmount": null
}
```

amount는 실제 입출금액이다. 카테고리가 없다고 행을 제외하지 않는다. 금액·날짜 추출 오류와 카테고리 미분류는 서로 다른 상태다.

### Spring → FastAPI 요청

```json
{
  "items": [
    {"itemIndex": 3, "counterparty": "가상편집도구", "description": "정기 결제"},
    {"itemIndex": 4, "counterparty": "가상카메라몰", "description": "카메라 할부 2회차 출금"},
    {"itemIndex": 5, "counterparty": "가상택시", "description": "촬영장 이동"},
    {"itemIndex": 6, "counterparty": "가상종합상점", "description": "물품 구매"}
  ]
}
```

지출 4건만 전달한다. itemIndex는 연결용이며 모델 특징에 넣지 않는다. ID·정답·정답 근거·분할 정보도 모델 특징에서 제외한다.

### FastAPI → Spring 기대 응답

```json
{
  "modelVersion": "category-v1-example",
  "predictions": [
    {"itemIndex": 3, "categoryCode": "SOFTWARE_LICENSE", "reviewRequired": false},
    {"itemIndex": 4, "categoryCode": "EQUIPMENT", "reviewRequired": false},
    {"itemIndex": 5, "categoryCode": "TRANSPORT", "reviewRequired": false},
    {"itemIndex": 6, "categoryCode": "UNCLASSIFIED", "reviewRequired": true}
  ]
}
```

위 응답은 목표 출력이며 실제 측정 결과가 아니다. 버전명도 예시다. 미분류 점수·임계값은 검증자료로 정한다. 응답 순서가 아니라 itemIndex로 연결하고 누락을 검사한다. 6번처럼 품목을 알 수 없는 거래는 별도 needs_info 검증자료로 관리하고 특정 용도의 정답을 억지로 붙이지 않는다.

### 코드와 화면 표시명

| 코드 제안 | 표시명 |
| --- | --- |
| YOUTUBE_SETTLEMENT | 유튜브 플랫폼 정산 |

| EXTERNAL_SUPPORT | 외부 후원（수입） |
| SOFTWARE_LICENSE | 소프트웨어（지출） |
| EQUIPMENT | 하드웨어（지출） |
| TELECOMMUNICATION | 통신비（지출） |
| TRANSPORT | 교통비 |

2026-10-19 사용자 변경: 외부 후원과 통신비를 추가하고 장비는 하드웨어·소프트웨어로 구분한다. 유튜브 플랫폼 안의 후원은 플랫폼 정산에 포함하고 외부 후원과 중복 집계하지 않는다. 미분류는 기존 목록의 카테고리 값으로 유지한다. 이 결정은 과거 제외 기록보다 우선한다. 영문 코드는 기존 프론트 선택지·DB 값과 대조할 제안이며, 전 구간에서 통일한다. 외주비 범주를 유지하더라도 면세 시연에 무조건 포함하지 않는다. 위 6건은 그대로 두며 새 카테고리 거래는 아직 생성하지 않았다.

## 4. DB 저장 형식

### 기존 테이블 확장 제안

현재 Mapper에서 아래 3개 테이블 사용을 확인했다. 실물 DDL은 미확인이므로 기존 스키마와 대조해 확장하고 같은 테이블을 중복 생성하지 않는다.

| 테이블 | 저장 필드 |
| --- | --- |
| FILE_META | 기존 파일 정보·소유자 + 파일 해시·분석 입력 연결·처리 상태 |
| TAX_INPUTS | taxInputId, userId, taxYear, periodStart, asOfDate, businessType, businessRegistered, basicDeductionAmount, basicDeductionReason, startupReliefAssumedEligible |
| TAX_TRANSACTIONS | transactionId, taxInputId, userId, sourceFileId, sourceItemIndex, transactionDate, transactionType, counterparty, description, amount, grossIncome, withheldTaxAmount, predictedCategoryCode, categoryCode, categorySource, extractionStatus, classificationStatus, modelVersion, isEdited |

기본공제는 TAX_INPUTS에 저장하고 일반 지출로 저장하지 않는다. 금액은 원 단위 정수(BIGINT 또는 DECIMAL 소수점 0), 날짜는 DATE, ID는 기존 자동 증가 숫자 형식과 맞춘다. SQL 열 이름은 기존 규칙에 맞춰 매핑하고 API는 camelCase·JSON 숫자를 사용한다. null과 0을 구분한다.

### 6건 저장 예시

공통 가상 ID: taxInputId=501, sourceFileId=301, userId=42. 사용자 ID는 인증 정보로 정한다.

| 원본 순번 | type | amount | grossIncome | withheldTaxAmount | categoryCode | categorySource |
| ---: | --- | ---: | ---: | ---: | --- | --- |
| 1 | INCOME | 980000 | 1000000 | 20000 | YOUTUBE_SETTLEMENT | RULE |
| 2 | INCOME | 967000 | 1000000 | 33000 | AD_SPONSORSHIP | RULE |
| 3 | EXPENSE | 35000 | null | null | SOFTWARE_LICENSE | MODEL |
| 4 | EXPENSE | 300000 | null | null | EQUIPMENT | MODEL |
| 5 | EXPENSE | 24000 | null | null | TRANSPORT | MODEL |
| 6 | EXPENSE | 50000 | null | null | UNCLASSIFIED | UNCLASSIFIED |

- predictedCategoryCode는 ML 추천을 보존한다. 수입 규칙 분류의 modelVersion은 null이다.
- 날짜·금액이 정상인 6건의 extractionStatus는 VALID다. 6번만 classificationStatus=NEEDS_REVIEW, 나머지는 CLASSIFIED다.
- 6번을 사용자가 소모품·소품으로 변경하면 categoryCode=SUPPLIES_PROPS, categorySource=USER, isEdited=true, classificationStatus=USER_CONFIRMED로 갱신한다. 원문·금액·원래 ML 추천 UNCLASSIFIED는 보존한다. 재추론으로 사용자 값을 덮어쓰지 않는다.
- 차감 세금을 실제 세액공제 계산에 활용한다면 국내 소득세·지방세·외국세 등을 상세 구분해야 한다. 이번 추가 납부·환급 계산에는 사용하지 않는다.

### 저장 순서·실패·중복

1. PDF 검증·추출 후 파일·기본정보·원본 거래를 연결해 저장한다. 분류 전 거래 상태는 PENDING이다.
2. 추론 후 추천과 최종 카테고리·상태를 갱신한다. ML 실패 시 원본은 유지하고 FAILED 상태·재시도를 제공한다.
3. sourceFileId+sourceItemIndex로 같은 행의 재시도 중복을 막는다. 현재 일반 INSERT에도 출처 연결을 추가해야 한다.
4. 동일 재업로드는 파일 해시로 검사한다. 다른 파일의 거래는 금액·날짜만 같다고 자동 삭제하지 않는다.
5. 수정 요청은 인증 사용자 소유권을 검증한다. 동일 연도라도 분석 입력 ID로 구분하고 기존 결과를 무조건 덮어쓰지 않는다.

비로그인 기본 분석은 만료되는 임시 세션에 보관한다. 결과 저장 클릭→가입·로그인 후 동일 분석을 계정 DB 데이터로 귀속한다. 임시 보관 방식·만료시간은 구현 시 확정한다. 파일은 공개 업로드 경로에 두지 않는다.

## 5. 화면 구분과 표시 형식

**사용자가 보여준 기존 화면의 통합 거래 목록을 유지한다. 수입·지출·미분류를 별도 영역으로 나누지 않는다.** PDF 추출·분류 결과를 기존 목록에 채운다. 기본정보의 새로운 화면 배치나 세전 수입·차감 세금의 별도 표시 위치는 합의되지 않았으므로 임의로 추가하지 않는다.

기존 열 구성: 계산 포함 / 구분 / 날짜 / 카테고리 / 내용 / 금액 / 상태 / 삭제. 전체 선택·전체 해제·선택 건수 표시도 유지한다. 아래 상태 문구는 의미를 설명하는 예시이며 새로운 상태 UI를 확정하는 것이 아니다.

| 계산 포함 | 구분 | 날짜 | 카테고리 | 내용 | 금액 | 상태 |
| --- | --- | --- | --- | --- | ---: | --- |
| 선택 | 수입 | 2026-03-05 | 유튜브 플랫폼 정산 | 유튜브 정산 | 980,000원 | 자동 입력·수정 가능 |
| 선택 | 수입 | 2026-03-08 | 광고·협찬 | 광고 협찬 정산 | 967,000원 | 자동 입력·수정 가능 |
| 선택 | 지출 | 2026-03-10 | 소프트웨어 | 정기 결제 | 35,000원 | 자동 입력·수정 가능 |
| 선택 | 지출 | 2026-03-12 | 하드웨어 | 카메라 할부 2회차 출금 | 300,000원 | 자동 입력·수정 가능 |
| 선택 | 지출 | 2026-03-13 | 교통비 | 촬영장 이동 | 24,000원 | 자동 입력·수정 가능 |
| 선택 | 지출 | 2026-03-15 | 미분류 | 물품 구매 | 50,000원 | 분류 확인 가능 |

미분류는 해당 행의 **카테고리 값**이다. 사용자는 같은 거래의 카테고리를 수정할 수 있고, 수정하지 않으면 미분류로 유지한다. 별도 미분류 목록이나 새 거래를 만들지 않는다. 카테고리만 미분류라는 이유로 계산 포함을 해제하지 않으며 선택된 거래는 합계에 포함한다.

**금액 인식 오류와 분류 미확인을 구분한다.** 금액·날짜 불확실은 별도 “원본 확인 필요” 상태로 표시하고 확정 거래처럼 합산하지 않는다. 카테고리만 미분류인 정상 거래는 계산에서 제외하지 않는다.

| 빈 결과 | 거래를 찾지 못함, 0원 분석 성공으로 표시하지 않음 |

## 6. 결과 화면 연결 및 기대값

| 결과 영역 | 기준 | 6건의 기대값 |
| --- | --- | --- |
| 수입·지출 요약 | 실제 입출금 | 수입 1,947,000원 / 지출 409,000원 / 차액 1,538,000원 |
| 세금 계산용 수입 | 세전 금액 | 2,000,000원 |
| 월별 차트 | 거래 날짜·실제 금액 | 3월 수입 1,947,000원 / 지출 409,000원 |
| 수입 출처 차트 | 실제 입금 기준 명시 | 유튜브 980,000원 / 광고·협찬 967,000원 |
| 지출 카테고리 차트 | 실제 출금 | 소프트웨어 35,000원 / 장비 300,000원 / 교통 24,000원 / 미분류 50,000원 |
| 산출 근거 기본공제 | PDF 기본정보 | 3,000,000원과 공제 설명 |

세전 기준 차트를 추가한다면 제목·범례로 구분한다. 차감 세금 53,000원을 새 수입·지출로 다시 더하지 않는다. 6번을 소모품·소품으로 수정하면 해당 차트 항목만 이동하고 총지출은 409,000원 그대로다.

최종 연간 세액은 전체 자료·미래 예측·해당 연도 세법·감면 확인 후 계산한다. 이 발췌에서 임의로 연간 세액을 만들지 않는다. 연간 결과에서는 실제/예상을 분리하고 세전 수입→경비→기부 인정액→기본공제와 사유→과세표준→산출세액→감면·세액공제→최종 예상세액을 보여준다. 추가 납부·환급액은 표시하지 않는다.

결과 조회는 비로그인도 가능하다. 결과 저장은 가입·로그인 후 원래 결과를 유지해 DB에 저장한다. 시뮬레이션은 로그인 사용자만 진입·계산·비교·저장 가능하다. 시뮬레이션 입력은 추가 세전 수입·업무 지출·적격 복지단체 기부이며 기준/변경 세액과 차이·기부 인정액을 표시한다. 노란우산 계산식을 이름만 바꿔 사용하지 않는다.

## 7. 현재 코드와 작업 위치

현재 PDF 업로드→Spring 추출→React 목록 연결 코드는 있고 ML 구현·연결은 없다. 실제 전체 실행은 미검증이다.

| TaxTransactionDto.java / TaxUploadMapper.xml | 위 필드와 출처·추천·사용자 수정 상태 저장·조회·갱신 |
